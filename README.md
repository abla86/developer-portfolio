## Evidence standard

The portfolio distinguishes:

**prototype → demonstration → verified → production-ready**

A repository is not described as production-ready merely because it builds or looks complete.

Where appropriate, the portfolio uses:

- source inspection
- automated tests
- CI
- linting and static analysis
- dependency/security controls
- documentation
- explicit architecture boundaries
- reproducible demonstrations

For research-support software, **software correctness is kept separate from scientific or methodological validity**.

## Interactive layer

The portfolio includes small interactive demonstrations to make implementation concepts visible rather than presenting only screenshots or prose.

Examples include:

- state machines
- network/state simulations
- defensive event simulations
- evidence-oriented interaction models
- capability navigation through the Yggdrasil-inspired engineering map

These demonstrations are deliberately separated from the serious project catalogue.

## Project maturity

Historical, training, archived and supporting repositories may remain visible on GitHub without being promoted as flagship products.

That distinction is intentional.

A project earns a primary position when there is enough:

1. implemented functionality
2. public inspectability
3. verification evidence
4. documentation
5. distinct technical value

to justify the claim.

## Engineering principle

> **Build → test → document → validate.**

The objective is a portfolio that can be inspected by a technical reviewer rather than a collection of technology keywords.

## Profile / portfolio relationship

The GitHub profile is the **map**.

The portfolio is the **deeper system**.

Repositories are the **implementation evidence**.

The visual tree on the profile represents capabilities and their relationship to the underlying work; it is not intended to replace the technical documentation.
